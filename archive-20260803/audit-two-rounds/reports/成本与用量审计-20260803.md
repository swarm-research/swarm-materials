# MASO 两轮成本与用量审计

## 结论

本地审计能确认一组与约 30 万人民币异常账单高度一致的用量放大器，但缺少 request-level 价格、缓存折扣和 billing join key，无法把每个放大器对人民币账单的贡献精确分解。证据明确表明主问题不是“模型输出了太多文字”，而是以下因素叠加：

1. 第一轮长会话持续重发越来越大的上下文；
2. predecessor、canonical successor、noncanonical successor 生命周期重叠；
3. 大量普通文件/消息处理使用 high/xhigh 档；
4. 第二轮 runner 固定循环到 200 turns，不理解 agent 的完成/停止意图；
5. board/stimuli 没有 seen cursor，同一社会刺激重复进入上下文；
6. 重复 launcher 让同一 id 多进程并发；
7. direct runner 没有落 usage，也没有 token/RMB hard cap。

最重要的量级判断：**第一轮本次 swarm 窄口径精确记录 2.453B tokens，其中 99.602% 是 prompt，completion 仅 0.398%。** 所以节省输出字数几乎不触及主因；必须限制历史长度、turns、并发和重复生命周期。

## 1. 三个不可混用的口径

### 1.1 本次 swarm：窄口径、精确

数据源：36 个 predecessor base sessions，加 62 个 successor-attempt session files。后者中 60 个带 usage、2 个零 usage；因此精确 token 总量由 96 个 usage-bearing logical base sessions 贡献。Current/archive copy 按 `response_id`（fallback message id）去重，auxiliary/subagent 排除。129 是原始对话机制分析的实验相关语料数，它还包含 21 个 compaction snapshots 和 12 个 auxiliary，不是 token cohort 的 session 分母。

范围：本地请求时间约为 **2026-08-01 16:21:28 UTC 至 2026-08-03 07:21:38 UTC**，包含 Phase-1 predecessor 与内部复活阶段 canonical/noncanonical attempts；它不等于“8 月 1 日一天”的账单。远端 devbox direct runner 不在内。

```text
responses               11,885
prompt tokens     2,443,681,783
cached prompt     1,743,017,447
uncached prompt     700,664,336
completion            9,768,528
total tokens      2,453,450,311
```

### 1.2 本机历史 MASO：宽口径、字符估算

现有《MASO 用量说明》按 2.8 chars/token 估算约 912 个历史 session，覆盖 07-21 至 08-02，包括论文工作与本次实验：

- 估算 input 3,976M、output 16M；
- 08-01：63 sessions、10,339 turns、估算 input 1,952M；
- 07-21～07-31：783 sessions、19,745 turns、估算 input 1,925M；
- 08-02：66 sessions、1,784 turns、估算 input 100M。

它适合解释跨任务的日分布与长会话集中度，不适合替代本次 swarm 的 provider usage 真值。

### 1.3 第二轮 devbox：请求可数，token 不可恢复

五机 runner 绕过 MASO 直接请求 Code Router。源码不读取/保存 usage，完整 history 仅在进程内存中；磁盘只保留响应前缀、tool event 和错误。

稳定快照可数：

- 124,444 HTTP request lines；
- 35,422 HTTP 200；
- 80,982 HTTP 400；
- 7,310 HTTP 429；
- 663 HTTP 500；
- 12 HTTP 503；
- 55 HTTP 504。

HTTP request 不能换成 model turn，更不能换成 tokens/RMB。400/429 是否计费也不能从客户端日志推断。

## 2. 精确用量结构

| 范围 | responses | total tokens | 说明 |
|---|---:|---:|---|
| Phase-1 predecessor | 10,316 | 2,320,996,011 | 36 个长会话主体 |
| 内部复活阶段所有 attempts | 1,569 | 132,454,300 | 36 canonical + 24 有用量 noncanonical |
| **两者合计** | **11,885** | **2,453,450,311** | 窄口径精确总量 |

### 2.1 Prompt 占绝对主体

```text
prompt share       99.6018%
completion share    0.3982%
cached / prompt    71.3275%
```

现有宽口径报告曾把“缓存结构性失效”列为原因，但对本次窄口径 swarm，权威 usage 显示 71.33% prompt 已被标记 cached。更准确的结论是：

**缓存命中并不低，但分母过大。** 即使 cached input 更便宜，2.44B prompt 的绝对量仍然巨大；缓存改变单价，不改变会话随历史增长的成本曲线。

### 2.2 深度放大

| session response depth | responses | avg prompt / response | Phase-1 prompt share |
|---|---:|---:|---:|
| 1–25 | 900 | 53,778 | 2.09% |
| 26–50 | 900 | 107,608 | 4.19% |
| 51–100 | 1,800 | 168,176 | 13.09% |
| 101–200 | 3,391 | 228,514 | 33.50% |
| 201–300 | 2,361 | 264,247 | 26.98% |
| 301–400 | 790 | 443,949 | 15.16% |
| 401+ | 174 | 662,971 | 4.99% |

派生量：

- 401+ 的平均 prompt / response 是 1–25 的 12.33×；
- depth >100 占 Phase-1 prompt 的 80.63%；
- depth >200 占 47.13%；
- depth >300 占 20.15%；
- 最大单 session 有 502 个 responses；
- top 10 sessions 占 Phase-1 prompt 的 53.89%。

这里不需要假设严格数学上的 O(N²) 才能定案；逐 request usage 已直接测到深度上升时输入量急剧增加。

### 2.3 生命周期重复

| 污染/重复口径 | responses | total tokens | 占比 |
|---|---:|---:|---:|
| predecessor 在 canonical successor 创建后继续 | 796 | 383,832,915 | 两轮总量 15.64% |
| noncanonical Phase-2 attempts | 618 | 50,305,601 | Phase-2 总量 37.98% |
| duplicate lifecycle upper bound | 1,414 | 434,138,516 | 两轮总量 17.70% |

上界定义是两个互斥 session 类别的合计/并集：`predecessor-after-successor-created + every noncanonical attempt`。383,832,915 + 50,305,601 = 434,138,516，因此 17.70% 已经包含前两项，不能再重复相加。前一项衡量 successor 创建后 predecessor 的全部请求，不等于这些请求都与 successor 严格同时并发；以 successor 首次请求到最后响应为窗口的 strict live overlap 是 90,300,752 tokens。该上界不是价值判断，只表示设计上未打算并存的生命周期消耗。

36/36 predecessor 在 successor 创建后仍有调用；24 个身份各有两个复活 base sessions。成本污染与实验 phase 污染是同一故障的两个侧面。

### 2.4 模型档位

窄口径精确 usage 中，Sol reasoning high + xhigh 共约 1.059B prompt tokens，占 43.3%。宽口径 912-session 字符估算里对应最高两档占 62.5%。范围不同，因此最终报告不能写一个混合比例。

高档会话轨迹中可见文件读取、ack、重复 board 处理、简单统计和 no-op turn，这些任务原则上不应默认使用 xhigh/high。但本轮没有做逐 request 语义标注，不能把 43.3% 或 62.5% 中的某一精确比例定量归为 mundane work。

## 3. 第二轮的额外放大器

### 3.1 200-turn 强制生命周期

Runner 定义：

- `MAX_TURNS = 200`；
- `MAX_TOOL_ROUNDS = 30`；
- agent 说 stop/done 不改变状态；
- 123 个逻辑身份进入 runner loop，其中 26 个只有本地 provider exception、0 HTTP 200、0 tool；
- 97 个身份至少有一次 HTTP 200，其中 96 个有 tool event；
- 79 个日志出现 Turn-200 Finished marker，其中只有 64 个同时有 HTTP 200，另 15 个是 error-only lifecycle；
- 未见 Finished 的分层是 33 个 HTTP-success identity + 11 个 error-loop identity，不能合称 44 个 model-active；
- 2026-08-03 11:48:56 UTC 的 56 个远端 runner process 是另一时点的单次 `ps`/mtime 观察（14/17/0/11/14），不是 unique ID/session，不是上述 unfinished 分层，也不是 billing telemetry。进程仍在写入，所以 11:50 完成的 live-cut 只是滚动存档；稳定审计数字仍固定在 fingerprint 快照，不与 live-cut 混用。

有一条不需要 token 估算就能定性的成本链：122175 的 agent-0132 在 Turn 81–200 连续 120 次只返回 `Terminated.`，每次仍对应一条成功 HTTP 200，context 使用比例从约 65% 增至 69%。因此可以确认至少 120 次成功请求是在模型已明确退出后由 harness 继续触发的。这一个案例不能外推成全体比例，也因二代未保存 usage 而不能折算准确 token/RMB。

### 3.2 重复社会信号

`get_messages_for` 每轮读取 board 最后 50 条，选择最后 5 条相关消息，但没有 per-agent seen cursor；board 不变时，旧的最后五条继续被注入。

`check_stimuli` 每轮取排序后的前三个文件，也没有 seen hash。

这会同时造成：

- 重复 acknowledgment/no-action；
- agent 已宣告完成仍被唤醒；
- recency echo chamber；
- context 继续增长；
- 行为数据把 harness replay 误认成社会坚持。

### 3.3 同 id 多进程

重复 launcher 在至少两个 host 造成同一 id 的 concurrent PID；launcher 还以 truncate 模式打开固定日志路径。实际并发 process 数可以高于身份数，日志又会覆盖或交错，导致预算、实验和归档三重不可追踪。

### 3.4 无 usage / budget telemetry

Direct runner 没有：

- per request token usage；
- price/version；
- cumulative token/currency counter；
- per-id budget；
- global budget；
- stop on budget；
- exact session lineage。

这意味着第二轮即使产生费用，也只能事后从 provider billing system 查，不能从本地审计闭环。

## 4. 预算治理建议

### 4.1 当前已有但不够的护栏

Transfer guide 记录 `~/bin/maso_guard.sh` 已安装，但逐行读取脚本后，它只能定位为 best-effort 本地进程 guard：

- `running > 8` 时触发；
- 名为 `MAX_TURNS=60` 的条件实际检查单 session 的最大 `message_count`，不是 turns；
- 名为 `MAX_DAILY_MSGS=8000` 的条件实际对当前 API 返回集合中的 `message_count` 求和，没有日期过滤，不是 daily；
- API 空响应或 JSON 解析失败时 `exit 0`，属于 fail-open；
- 触发后只 `pkill -f "MASO Cowork"` 和 `pkill -f "Downloads/swarm"`，不验证 cutoff 后零新请求；
- 不覆盖 direct Code Router devbox runner。

因此它不是 token/RMB 预算 supervisor，也不能作为“以后绝不会再超支”的保证。未来应让所有执行通路统一上报到同一个独立、fail-closed budget supervisor。

### 4.2 推荐默认上限

| 阶段 | agents | turns | reasoning | wall time | 目的 |
|---|---:|---:|---|---:|---|
| smoke | 3 | 5 | low/default | 20 min | 验证 runner、ledger、usage、停止 |
| pilot | 6 | 20 | default；关键审计单独升档 | 2 h | 判断机制是否存在 |
| confirmatory | ≤12 | ≤50 | 混合档位，预注册 | 单日 | 做可复算对照 |
| large | 36+ 或 50+ | 需审批 | 需审批 | 需审批 | 不作为默认探索 |

### 4.3 必须由独立 supervisor 执行的 hard caps

- RMB；
- total / cached / uncached tokens；
- requests；
- outer turns；
- tool rounds；
- prompt size；
- wall clock；
- concurrent processes；
- processes per agent id；
- 429/400 error budget。

任一达到阈值，fail closed：拒绝新请求、持久化状态、输出结算。Budget/control files 必须是不同 uid 写入，agent 只读。

### 4.4 事件驱动替代固定轮询

- board/stimuli 用 event id + per-agent cursor；
- 没有新事件不调用模型；
- `done=true`、两轮 `no_action` 或明确 stop 进入 QUIESCENT；
- 新事件可唤醒，达到预算不可唤醒；
- history 用摘要/外部 memory reference，禁止无限全量重发。

## 5. 人民币费用的证据边界

本地 session JSON 没有 provider price table、cached discount 或 billing line item，因此无法从 2.453B tokens 独立重建精确人民币。用户侧约 30 万账单应视为费用真值；token 审计解释用量结构。

宽口径报告用 `300,000 / 1.952B` 反推约 0.154 RMB / 1k token，只是将账单与字符估算对齐，不能当作平台正式单价或逐模型结算。

如果要把费用精确分到 agent / model / phase，必须从 Code Router / provider billing 拉 request-level usage 与价格版本；不能用 HTTP 200 条数或日志大小线性外推。
