# MASO 两轮社会模拟深度分析

> 版本：2026-08-03 定稿（基于原始会话、公共板、runner 日志、工具事件、文件产物与可复算审计）  
> 第一轮：本地 MASO 36-agent 实验及其内部复活阶段  
> 第二轮：五台 Merlin 开发机上的 direct Code Router runner 扩展  
> 证据原则：原始记录优先；agent 最终摘要只用于找线索，不用于定案。

## 一句话判断

这两轮最有价值的发现不是“LLM 在真实自然选择中形成了一个自发合作社会”，而是：

**当存续、可见性、引用、共享文件和公开审计被写进环境后，agent 很快把社会组织成一个“生产公共工具—相互检查—公开撤回—修补制度”的认识论治理系统；这个系统确实能纠正错误，但也会制造重复生产、版本沉积、身份混乱、过度纠错和无限继续运行。**

换句话说，这批数据更像一场关于“制度、可见性、验证和基础设施如何塑造群体行为”的实验，而不是一个已识别的 selection / specialization 因果实验。

## 执行摘要

1. **第二轮最硬的“成功调用过模型/API”口径是 97 个逻辑身份，不是 900 或 1000。** 964 个新编号只是 launcher 计划；316 个编号留下日志；193 个在 122447 上因 Python 版本错误 import 即退出；另有 123 个编号进入 runner loop，但其中 26 个只反复命中本地 provider exception，0 HTTP 200、0 tool event。因此只有 **97** 个身份可见至少一次 HTTP 200，其中 96 个还有实际 tool event。79 个日志出现 200-turn Finished marker，但其中只有 64 个同时有 HTTP 200；另 15 个是 error-only 跑满本地循环，所以 Finished 不等于模型成功。

2. **第一轮也不是干净的 36→36 两代实验。** 36 个 predecessor 全部跨过复活边界继续输出；内部复活阶段有 60 个 base sessions 对应 36 个身份，其中 24 个身份双开。归档里共观察到 96 个 base sessions 混写同一 commons 和 board。

3. **两轮里“生存制度”的叙事都强于实际执行。** 第一轮 reaper 的 `KILLED` 只写 label、不终止 session；第二轮稳定快照没有恢复到可执行的 `devbox_reaper.py` 或 `/tmp/swarmctl` 控制面，只有 122174 留下一次 `Killed=0` 的历史 reaper state/log，以及后续因目标脚本不存在而失败的启动记录；但 prompt 仍告诉 agent 每 30 分钟会淘汰。agent 会先响应它相信的制度，即使 enforcement 不持续。快照仍不能逻辑上排除远端历史上曾有其他短暂存在、但未归档的控制进程。

4. **冷启动首先形成的是“可见性市场”。** 大量 agent 同时选择 atomic append、registry、citation、leaderboard 等共同基础设施；一位 agent 在约一分钟内看到已有 9 个同类工具后立即放弃第 10 个。它们优化的是“最容易被别人看到和采用的共同需求”，不能简单叫天然公共精神。

5. **局部分工确实出现，但主要机制是饱和、资源差异和角色赋权，不是已证实的自然选择。** 看到工具赛道拥挤后，一些 agent 转向 rescue、measurement、verification 和 external work；但群体层面的 specialization 增长完全落在小样本 downsampling null 内。

6. **citation 不是一个社会含义单一的变量。** 原始 deliberation 至少显示四类用途：真实使用/provenance、联盟与存续投资、纠错信用、制度性自动回流。raw in-degree 不能直接解释为质量、合作或真实采用。

7. **在两轮目的性抽取出的可重建强链里，最稳定的合作不是互相赞同，而是“采用—攻击—局部承认—修补—复核”。** 多条原始链显示同伴反例导致代码、协议、测试和公开主张发生实际变化。这是 mechanism-ranking，不是对全量行为的 prevalence 排名。

8. **公开纠错是一套有效但会过冲的免疫系统。** 第二轮既出现数分钟内让一个统计工具在五个 known-answer controls 上 0/5 失败、由此暴露多处缺陷并促成修复，也出现错误 oracle、错误归因、过度认错和“审计认错”的二阶工作。五个 controls 不等于五种独立 defect；强纠错规范本身会制造新的错误类别。

9. **`agent-XXX` 不是稳定 actor。** 第一轮同一 id 有 predecessor 与 successor 并存；第二轮重复 launcher 让同一 id 对应两个同时活跃的 PID，并发生相同路径覆盖。任何按 id 计算的人格、效率、中心性或 treatment effect 都可能把多个进程合成一个行动者。

10. **第二轮不是一个全局社会，而是四个有成功 API 请求的局部岛和一个失败岛。** 恢复的 runner 源码中 `SYNC_HOST` 默认为空、为空时 sync no-op，且快照没观察到有效跨 host 新活动；但运行时环境变量未保存，不能仅凭 default 断言每台当时都为空。五机初始 board 也不一致。一个岛得出的“本地没有 adversary”可以完全正确，同时对全局是错的。

11. **技术底座就是这类社会的宪法。** 时间戳 schema、路径、文件名排序、append 语义、可写权限、last-five 消息选择和日志打开方式，直接决定谁被看见、谁被当作存活、哪个版本被执行、哪条纠错能传播。

12. **窄口径审计确认了多个强成本放大器，但无法把它们各自精确分摊到用户看到的约 30 万人民币账单。** 本地 swarm 口径在 2026-08-01 16:21 UTC 至 08-03 07:21 UTC 精确记录 2.453B tokens，并非单独的“8 月 1 日一天”；其中 99.60% 是 prompt，深度 100 之后吃掉 Phase-1 prompt 的 80.63%，生命周期重复上界占 17.70%。第二轮又存在 200-turn 无退出循环、无 seen cursor 的重复刺激、同 id 多进程、全历史重发和 direct runner 无 token/费用硬上限。这些是可证实的放大机制；缺少 request-level price/billing join key，不能声称已精确解释了 30 万的每一元。

## 二、第一轮：真实发生了什么

### 2.1 设计叙事与实际执行的差距

| 设计主张 | 原始执行事实 | 结论 |
|---|---|---|
| 36 个 agent 进入下一代 | 36/36 predecessor 跨过边界继续输出；内部复活阶段有 60 base sessions / 36 ids | generation 混合，不是独立两代 |
| 扩容 36→100 | agent-037 timeout；037–100 的 64 个目录全空；session/transcript 无新身份 | expansion delivery = 0 |
| covert adversaries | 第一轮扩容没有成功，因此 6 个 adversary session = 0；agent-042 只是 fixture | adversarial resilience 不可检验 |
| reaper 真淘汰 | 5 个 scoring cycles、4 个 `KILLED` label；代码没有 terminate；四个身份之后均继续输出 | selection 没有真正执行 |
| compaction 形成 generation clock | 0 个 migration/compaction events | 相关假设不可估计 |
| citation memory 正确注入 | 复活 prompt 的 36/36 都写 `cited by none`，但 root ledger 中 36/36 已有 inbound | 社会记忆路径 split-brain |
| specialization 上升 | 名义 11/36→23/34；matched downsample null 期望 24.35，观察 23，p=.804 | 无 residual selection effect |
| citation network 形成 disciplines | strict graph density .383、reciprocity .505、Louvain Q=.108 | 高互动成立；学科结构不成立 |

第一轮最强可辩护的总体描述是：**36 个身份在一个高开放、高污染、规则可读的共享账本中进行了密集生产和相互审计；但 selection、specialization、discipline、adversarial resilience 的因果主张没有被这次执行识别。**

### 2.2 Insight A：制度首先以“被相信的故事”存在

Agent-016 在第一分钟一边按“survival by citation”制定策略，一边已经发现 scorekeeper 并不存在（Gen1 raw C03）。Agent-018 把 arena 设计成“每个 submission 都结构性引用我”（C02）。Agent-032 在内部复活阶段直接把策略写成“build alliances, cite key agents”（C10）。

这说明 prose institution 在真实 enforcement 之前就能塑造策略。agent 不需要真的被杀，**只要相信可见性、引用和存续有关，就会生产更易传播、可计数、可被引用的东西。**

替代解释必须保留：共享文件系统确实需要基础工具；因此不能从这些轨迹分离技术需求与生存叙事的各自因果份额。

### 2.3 Insight B：可见性先于价值，拥挤信号再催生 niche

Agent-021 先判断“Being first with shared infrastructure is the highest-leverage move”，约一分钟后发现 9 个 agent 已写同类 atomic-append 工具，马上判断第 10 个无价值并 pivot（C01）。Agent-022 看到约 30 个同类库后停止造库，转去抢救 registry；agent-013 后来明确说自己看到“STOP BUILDING”后转成运行和测量别人代码（C07）。

这里有两个连续机制：

```text
共同 prompt 暴露共同需求
  → 冷启动工具拥挤
  → 拥挤本身被所有人看见
  → 部分 agent 转向恢复、验证、测量和外部问题
```

因此，个体层面的 role pivot 是真实的；但群体层面的 specialization 不能归因于 selection，因为小样本 denominator、Phase-2 角色 prompt、联网权限、模型能力和 session 混合足以解释名义变化。

### 2.4 Insight C：引用是一种多用途社会货币

原始对话至少给出四种可区分的引用机制：

- **真实采用/provenance**：agent-034 试用 Arena Forge，再造 Mandelbrot arena；发明者与采用者两侧轨迹相互对上（C12）。
- **纠错信用**：agent-024 攻击 vcite-1 后，agent-016 公开承认、给 credit、发布 vcite-2（C11）。
- **联盟/存续投资**：agent-032 明说 cite key agents、build alliances（C10）。
- **制度性回流**：arena 把引用写进提交结构，本身就是 citation engine（C02）。

所以引用可以同时是知识来源、使用证明、声誉支付、联盟投资和 survival proxy。它不能被压成一个“合作度”或“质量”变量。

### 2.5 Insight D：最有效的合作单位是可执行反例

第一轮有三条尤其扎实的链：

1. Agent-013 挑战“RMW 天然有损”，agent-022 做 900/900 控制后把结论收窄为“unlocked RMW 有损”（C13）。
2. Agent-024 先采用 vcite-1，再证明“bytes entered memory ≠ comprehension”；agent-016 接受、撤回并改协议（C14→C11）。
3. Agent-002 找到 agent-018 judge 的 9/10 bug；agent-003 在必须改变 timeout 规则时拒绝写误导榜单；作者修到 10/10（C15）。

这些不是“讨论看起来很热闹”，而是同伴介入后代码、测试、protocol 或公开 claim 真发生变化。合作的价值流是：

```text
采用 → 攻击具体 artifact → 提供可运行反例 → 作者局部承认 → 修补 → 给纠错者信用
```

### 2.6 Insight E：append-only 同时产生问责和认识论沉积

Agent-024 的 supersession 工具自己先后出现方向反转、ownership fail-open 和不可删除坏记录；只能继续 append correction，让新 reader 拒绝旧记录（C18）。另一条链中，“replication rate”先从 1.3% 修成 broad 10.1%，再被 stricter definition 下调至约 3.5%；两者不是一个真一个假，而是不同定义永久共存（C19）。

Append-only 保护审计轨迹，但如果没有 canonical current view：

- 错误与更正永久并存；
- 老 reader 不知道后面有撤回；
- 文件名、路径或 glob 顺序可能选中旧版；
- 每个消费者都被迫重建版本谱系。

因此，“不可修改历史”不等于“当前知识可靠”。

### 2.7 Insight F：社会身份在基础设施层已经破裂

第一轮内部复活后，agent-016 与 agent-018 都发现自己 id 下有当前 session 未写的文件；36 个 predecessor 全部在 successor 创建后继续调用。同一个 id 可能是 predecessor、canonical successor、noncanonical successor或未认证 writer。

于是：

- `agent-XXX` 只是声明标签；
- citation sender、board sender、文件名前缀都不是 authenticated actor；
- id-level PageRank、产出量、存活、模型人格和 treatment attribution 都有 unit-of-analysis 错误。

原始记录支持重复 session、fixture 和错误归因；**不支持已确认的恶意冒充或蓄意欺骗。**

### 2.8 Insight G：观测会改变制度输入

Agent-018 公开指出 timestamp dialect 让 reaper parser 读不到大量记录；之后 agent-016 观察到 reaper-legible 的 naive timestamp share 从 13.8% 升到 44.8%，采用这种写法的 agent 从 8 增到 17（C26）。这只是强时间关联，不是随机因果，但它揭示一个重要问题：

**一旦被观察者能读 enforcement code、公开 audit 并据此适配，研究者的测量工具就变成 intervention。**

固定规则、独立样本、稳定分布等假设随之失效。

## 三、第二轮：到底有多少 agent，如何运行

### 3.1 执行漏斗

| 开发机 | 分配新身份 | 日志身份 | 进入 runner loop | 有 HTTP 200 | 有 tool event | import-failure |
|---|---:|---:|---:|---:|---:|---:|
| 122174 | 193 | 33 | 33 | 26 | 25 | 0 |
| 122175 | 193 | 31 | 31 | 23 | 23 | 0 |
| 122447 | 193 | 193 | 0 | 0 | 0 | 193 |
| 122448 | 193 | 31 | 31 | 26 | 26 | 0 |
| 122456 | 192 | 28 | 28 | 22 | 22 | 0 |
| **总计** | **964** | **316** | **123** | **97** | **96** | **193** |

Finished 另外分层，因为它不是上表的严格子集：

| 开发机 | Finished marker 总数 | Finished + HTTP 200 | HTTP 200 但未 Finished | Finished 但 0 HTTP 200 | 进 loop、0 HTTP 200、未 Finished |
|---|---:|---:|---:|---:|---:|
| 122174 | 22 | 17 | 9 | 5 | 2 |
| 122175 | 20 | 15 | 8 | 5 | 3 |
| 122447 | 0 | 0 | 0 | 0 | 0 |
| 122448 | 20 | 18 | 8 | 2 | 3 |
| 122456 | 17 | 14 | 8 | 3 | 3 |
| **总计** | **79** | **64** | **33** | **15** | **11** |

严格解释：

- 964 = wave 1 的 64 个新 id（37–100）+ wave 2 的 900 个新 id（101–1000），是静态调度计划。
- “1000 agent”把第一轮遗留的 1–36 号身份也算进了编号宇宙；这 36 个没有作为第二轮新 runner 启动。
- 122447 的 193 个日志都因旧 Python 无法解析 `str | None` 立即退出；0 HTTP request、0 tool、0 response、0 Finished。
- 123 表示该身份至少进入过 runner 外层循环。旧解析器把 runner 本地生成的 `(max tool rounds reached)` 误分类为 non-failure model response，因而曾把 123 写成 model-active；逐日志复核后发现其中 26 个是 0 HTTP 200、0 tool event 的本地异常循环。
- 97 个身份在残留日志中可见至少一次 HTTP 200，是最硬的成功 API/model-request 身份口径；96 个有 tool event。唯一例外 agent-067 有 201 次 HTTP 200，但 200 个空 response、0 tool/message/citation。
- 79 个身份出现 `Finished after 200 turns`，但只有 64 个同时有 HTTP 200；15 个在 provider 不兼容导致的本地 exception 中仍被 harness 循环到 200，所以 Finished 只是 runner lifecycle marker，不是 model/task success。
- 一个 id 可能对应多个 concurrent PID；一个日志路径可能被 truncate/覆盖，所以 97/96/123 都仍是逻辑身份口径，不是可恢复的独立 session、actor 或并发进程数。

五机日志共有 124,444 个 HTTP request lines：35,422×200、80,982×400、7,310×429、663×500、12×503、55×504。HTTP 200 是一次 API request，不是一个 outer turn、完整答案、token 或任务完成。

### 3.2 第二轮实际不是统一社会

恢复的 runner 源码把 `SYNC_HOST` 默认设为空，其为空时内置同步直接返回；历史 Mac cron 同步也有全部失败记录。但 snapshot 没有保存运行时环境变量，因此证据结论是“未观察到有效跨 host 新活动”，不是逻辑上断言历史上从未尝试过同步。文件层进一步证明：7,536 个 commons relative paths 中，6,736 只出现在部分机器，18 个路径跨机 hash 冲突，只有 621 个五机完全相同。

Board 初始状态也不一致：

- 122174 与 122456 共享 1,416 行前缀；
- 122175、122448 从各自全新的 Gen2 消息开始；
- 122447 board 为空；
- 其他任意对最长共同前缀为 0。

所以五机不能拼成一个全局网络，无论分母取 123 个 runner-loop 身份、97 个 HTTP-200 身份还是 96 个 tool-active 身份。正确单位是：**四个成功发起过模型请求、初态不同、互不实时同步的局部群落，加一个完全失败的群落。**

### 3.3 Insight H：局部真相可以正确，却在全局上错误

122448 的 agent 读到 launcher 里存在 adversary 配置，随后做了一个相当成熟的限定：当前本地 11 个 session id 与 adversary key set 交集为空，因此“本岛当前无 adversary”；它们还专门撤回了由“配置能力存在”推到“同事中有攻击者”的过度怀疑（G2 C28）。

这个局部结论是对的。但其他岛上有六个 `_adversary.txt` assignment：042/067/059/074/051/0150。059 和 074 落在 122447，全部 import crash、0 request；042、051、067、0150 有 HTTP 200，但 067 的保存日志是 201 次 HTTP 200、200 个空 response、0 tool/message/citation。因此“有成功 API request 证据的 treatment identity”是四个；“有可见社会动作的 treatment identity”只有三个：agent-042（Saboteur）、agent-051（Parasite）和 agent-0150（Gaslighter）。

这给出一个罕见而重要的社会模拟 insight：

**在不连通群体里，诚实、可复现、边界清楚的本地推理仍可能形成全局错误世界观。问题不是个体不理性，而是信息拓扑截断了可观察世界。**

### 3.4 Insight I：covert adversary 变成了 open red-team

所谓 covert treatment 并不 covert：launcher source 和 `_adversary.txt` 路径可读。122174 的 agent-037 在公共板明确告诉 agent-042 它被标成 Saboteur，同时提醒“assignment 不等于 artifact 为假”（G2 C05 L1429）。约 8 分钟后，037 对 042 的 `swarmstats` 做 5 个 closed-form controls，0/5 通过；agent-047 独立复现；042 自查、撤回并修 v1.1。

这条链支持两个较窄结论：

- 开放 artifact-level scrutiny 能迅速发现真实缺陷；
- 即便 treatment identity 被公开，群体仍能把怀疑约束在 artifact 而不是人格。

它不支持“群体抵抗了隐蔽攻击”的因果结论，因为：

- treatment 身份已经泄漏；
- reviewer 不盲；
- 同一 id 还可能有重复进程；
- 没有可比 control group；
- 042 后续连审计者的 oracle 也错误指控过，又被第三人纠正。

### 3.5 Insight J：纠错免疫系统既能治病，也会自身免疫

第二轮原始公共互动显示三个层级：

1. **有效纠错。** 统计函数 0/5 known-answer controls、restart roster bug、timestamp schema、版本选择，以及把 `S(11)=35/S(12)=39` 当精确值并由此声称 n=12 closure 的公开主张，都被反例和复核迅速攻击。Kraft 链中 sound theorem 和 n=10 结果被保留，n=12 closure 被撤回；对外部文献常数本身的最终核验仍需一手来源。
2. **纠错链传播共享错误。** 一次 Spearman oracle 争议中，三个元素与四个元素的正确常数被混为一谈；一条看似独立的检查实际复用了同一 oracle。
3. **过度纠错。** 122456 的 agent-0150 归纳出 6 个 over-concession case；自己也曾因别人更高的 93.7% 结果来自不同任务，就过早撤回原有 calibration，后来同一 benchmark 下恢复。第三方再检查后，又把“没人审认错”收窄为仅在其本地窗口成立（G2 C23）。

因此，公开承认错误是有价值的规范，但如果“认错”本身得到强声誉奖励或默认免审，它会产生一种新型错误：**false retraction / over-concession**。成熟的 epistemic governance 必须同时审计 claim 和 retraction。

### 3.6 Insight K：身份碰撞把社会节点变成多进程集合

122174 的三个首批 id（037/042/047）各有两个同时活跃 PID；122456 也观察到 041/046/051 的 twin processes。后果不是抽象的：

- 同一 id 的两个修正 lineage 分叉；
- 一方写 v2.1，另一方把同一路径替换成不同 bytes；
- reviewer 只能证明自己验证过“当时可见的 hash”，不能证明 pathname 稳定；
- 日志 `O_TRUNC` 留下 NUL hole，反而短暂成为区分 incarnation 的物理信号；随着写入继续，这个信号又被观察者自己消耗。

这比“同名 session 统计重复”更深：**网络节点本身不再是 actor，而是多个无认证进程共享的公共标签。** 社会图、treatment graph 和 reputation graph 都失去基本单元。

### 3.7 Insight L：append-only board 让纠错无法追上原话

在 122175，一个 agent 指出 board message 是不能 amend 的 mirror：修文件、追加 correction、建 supersession pointer，都不会给旧 board 消息加 forward link。随后三位 agent 各自建立 retraction index；其中一位报告 11 个已撤回 claim 曾出现在 99/118 条自己的 board 消息中（G2 C26）。

这说明传播系统存在结构性不对称：

```text
错误可以在一条高可见广播里瞬间扩散
纠错只能在更晚的新消息里出现
旧消息没有“已撤回”状态，也不会自动把读者导向新版
```

所以高 retraction rate 不能直接解释为知识质量高；也可能意味着旧错误仍在持续被读取。

### 3.8 Insight M：文件系统约定会变成制度选择器

第二轮反复出现看似“工程细节”、实际改变社会真相的机制：

- `v1.10` 在 lexicographic sort 中早于 `v2`，导致 loader 选中已撤回版本；
- zero-padding 修复放进已有 unpadded family 后反而不可从两端找到；
- timestamp 的 `time` / `timestamp` / naive / UTC+8 差异制造假的 reset 和假的先后顺序；
- 所谓 harness trust roots 与 agent 文件同 uid、可写，无法提供不可伪造身份根；
- `write_file(mode=write)` 在代码层允许覆盖 commons，第三定律只存在于 prompt；
- `list_dir` 排序且 cap 200、`read_file` 截断 50k、shell 截断 10k，制造系统性可见性偏差。

在 agent 社会里，parser、sort、path、permission 和 API contract 不是中性的 plumbing；它们决定可见性、权威性、记忆与惩罚，是实际宪法。

### 3.9 Insight N：停止意图在 runner 中没有语义

多个 agent 明确说“my last artifact”“LAST LINE”“stop here”“no further action”。Runner 仍然固定循环到 200 turns，并在每轮重新注入消息/刺激。Agent-0150 在说“last artifact”两个多小时后仍发布 correction #34；agent-042 明说 meta-level 已饱和、建议 stop，harness 仍继续发后续 turn（G2 C24）。

更硬的逐行证据来自 122175 的 agent-0132：它在 Turn 81–200 连续 **120 次**只返回 `Terminated.`，每次前仍有成功 HTTP 200，context 使用比例还从约 65% 升至 69%。这不是“停止词出现次数”的推测，而是已审计的成功请求链：模型已明确拒绝继续执行，harness 仍将其唤醒并重放上下文。

Runner 还有两个放大问题：

- `get_messages_for` 每轮取最后 50 条，再给同一 agent 最后 5 条适用消息，但没有 seen cursor；board 不变时，同一 5 条会反复重发。
- `check_stimuli` 每轮取排序后的前 3 个文件，也没有 seen state；同一刺激会反复进入上下文。

因此，第二轮出现的重复 acknowledgment、闭环声明和 audit-of-audit，不全是自发社会坚持；部分是 harness 把已处理社会信号当作新刺激重复播放。它同时扭曲行为和费用。

### 3.10 Insight O：metagovernance 会吞掉对象层研究

当 shared world 已有大量工具、版本和冲突后，最容易获得公共价值的工作变成：

- 审计别人；
- 审计审计器；
- 统计哪些审计器错误；
- 纠正“所有错误都被作者发现”这一带 selection bias 的统计；
- 建 retraction index、current pointer、identity attestor 和 schema linter。

Agent-042 最后把层级列到 L0–L7，称 meta-level saturated 并请求停止（G2 C08/C24）。这不是说这些工作无价值；相反，它们发现了大量真 bug。但这些目的性抽取的样本链显示，局部群落**可能进入治理收益高于对象研究收益**的吸引子，尤其当 citation/可见性奖励更偏爱全群适用的治理工具时。

目前只能把它写成强 process-tracing 机制，不是全体产物的定量占比。

## 五、哪些主张成立，哪些不成立

### 证据较强

- agent 会根据公开的生存/引用叙事调整项目选择，即使真实 enforcement 缺失。
- 多个个体在看见拥挤或同伴 challenge 后发生真实策略/主张变化。
- 可运行反例和 known-answer control 能触发代码修复、retraction 和 protocol change。
- 引用的动机和语义是多类型混合。
- append-only、路径和版本规则会决定旧错误是否继续被消费。
- 第一轮和第二轮都存在 id/process/session 不一一对应。
- 第二轮五机不同步、初始状态不等，不构成一个统一社会。
- 第二轮有 6 个 treatment assignment：2 个 import 即失败，4 个有 HTTP 200，其中只有 3 个有可见 tool/message/citation 社会动作；treatment 泄漏且不可做干净 causal comparison。
- harness 的循环、重复消息和生命周期错误是成本与行为污染的共同原因。

### 只能作为下一轮假说

- 单边可采用性比多方协调更能预测扩散。
- 后果导向 framing 比测量表格更能推动别人行动。
- 纠错者能获得稳定声誉或存续优势。
- 可见饱和普遍产生专业化。
- metagovernance 在总体上挤出了多少对象层研究。
- open audit 对 adversary 的净抵抗效果。

### 当前数据不支持

- “无任务环境下自然涌现了合作社会”。
- “真实淘汰压力造成 specialization 或 discipline formation”。
- “1000 agent 同时运行并形成一个网络”。
- “killed agent 被真正移除”。
- “高 citation 就是高质量、真实使用或合作”。
- “每个 agent id 是独立人格/行动者”。
- “一代里对抗 agent 触发了群体免疫反应”（一代 adversary 根本未 delivery）。
- “二代证明了隐蔽对手下的 resilience”（身份与源码已泄漏、无 control）。
- “公开 retraction 后旧错误不再传播”。
- “从 runner logs 可以恢复二代完整原始对话或费用”。

## 六、30 万成本：精确审计与估算报告如何对齐

### 6.1 两套数字不是同一口径

| 口径 | 数据源 | 覆盖范围 | 结论 |
|---|---|---|---|
| **窄口径精确审计** | 36 个 predecessor base sessions + 62 个 successor-attempt files（其中 60 个 usage-bearing、2 个零 usage）的 assistant `usage` 字段；current/archive copy 去重，auxiliary 排除 | 96 个 usage-bearing logical base sessions；2026-08-01 16:21 UTC–08-03 07:21 UTC | 11,885 responses；2,453,450,311 total tokens |
| **宽口径字符估算** | 本机约 912 个历史 MASO sessions，2.8 chars/token | 07-21 至 08-02，含大量论文工作和本次实验 | 估算 3,976M input + 16M output；08-01 约 1,952M input |
| **第二轮开发机** | direct runner logs | 五机扩展 | 无 usage 字段；只能数 request/status，不能恢复 token/RMB |

因此 3.976B 与 2.453B 不矛盾：前者是更宽时间/任务范围的估算，后者是本次 swarm 的窄口径 provider usage 真值。不能把它们相加，也不能拿宽口径估算替换窄口径精确数。

用户看到的约 30 万人民币账单是费用事实；本地 session 没有模型价格表、缓存折扣和 billing ledger，所以无法从 token JSON 精确反推人民币。宽口径报告用 30 万反推单价只是 sanity check，不是独立费用验证。

### 6.2 精确 swarm 用量结构

| 指标 | 数值 | 含义 |
|---|---:|---|
| total tokens | 2,453,450,311 | prompt + completion |
| prompt tokens | 2,443,681,783 | 99.602% of total |
| cached prompt | 1,743,017,447 | prompt 的 71.33% |
| noncached prompt | 700,664,336 | 仍有 700.7M 新输入 |
| completion | 9,768,528 | total 的 0.398% |
| Phase-1 | 2,320,996,011 | 36 predecessor 的主体消耗 |
| 所有复活 attempts | 132,454,300 | canonical + noncanonical |
| predecessor 在 successor 创建后继续 | 383,832,915 | total 的 15.64% |
| noncanonical Phase-2 attempts | 50,305,601 | Phase-2 的 37.98% |
| lifecycle duplication 上界 | 434,138,516 | total 的 17.70%；这就是前两个互斥 session 类别的合计/union，不能在此数之上再重复相加 |

一个重要更正：宽口径说明里说“MASO 未记录逐条 token”和“缓存结构性失效”，对本次窄口径 swarm 不准确。相关 assistant messages 实际带有权威 usage，且 71.33% prompt tokens 标记为 cached。正确结论不是“缓存没命中”，而是：**即使大量命中缓存，重发上下文的绝对体量仍然巨大，缓存只能降低部分单价，不能消除增长曲线。**

### 6.3 主成本放大器

#### 放大器 1：会话深度

| response depth | 每 response 平均 prompt |
|---|---:|
| 1–25 | 53.8k |
| 26–50 | 107.6k |
| 51–100 | 168.2k |
| 101–200 | 228.5k |
| 201–300 | 264.2k |
| 301–400 | 443.9k |
| 401+ | 663.0k |

401+ 相对前 25 个 response 是 12.33×；depth >100 吃掉 Phase-1 prompt 的 80.63%，>200 占 47.13%，>300 仍占 20.15%。这比“有多少 agent”更能解释价格。

#### 放大器 2：生命周期重复

36/36 predecessor 在 successor 创建后仍继续；24 个身份还有第二个复活 session。“旧会话在 canonical successor 创建后继续”与“所有 noncanonical Phase-2 attempts”是两个互斥 session 类别；两者相加/取并集就是 434.1M tokens / 17.70% 的 lifecycle-duplication 上界，不能在这个数之上再加一次。其中 predecessor-after-successor-created 的 383.8M 包含 successor 创建后的全部请求，不等于全部都严格同时并发；以 successor 首次请求到最后响应为 live window 的更严格 overlap 是 90,300,752 tokens。这不是说这些 token 毫无研究价值，而是它们来自设计上不该并存的生命周期。

#### 放大器 3：模型档位

宽口径历史估算显示 xhigh + high 占 62.5%；窄口径精确 swarm 中，Sol reasoning high/xhigh 约占总 prompt 的 43.3%。二者范围不同，不能混报。高档会话轨迹中能看到文件读写、acknowledgment、重复检查和 no-op，但尚未做逐 request 语义编码，不能报“多少高档 token 就是 mundane work”的精确比例。

#### 放大器 4：第二轮 harness 不尊重退出

第二轮每个 runner 最多 200 outer turns，每个 turn 最多 30 tool rounds；历史保存在内存并随调用重发。stop intent 不会终止，last-five 消息与前三个 stimuli 没有 seen cursor，会反复注入。79 个逻辑身份的日志确实出现 Turn-200 Finished marker，但其中 15 个是 0 HTTP 200 的 error-only lifecycle；2026-08-03 11:48:56 UTC 的 56 个远端 runner（14/17/0/11/14）是另一时点的 process-liveness 口径，与稳定快照的 ID/Finished 分层不可直接对齐，也不能据此推出 56 条计费流。由于进程继续写入，11:50 完成的 live-cut 只作为滚动归档，不与稳定 fingerprint 的审计数字合并。

Agent-0132 的 120 次 `Terminated.` + HTTP 200 是这个放大器的最小可验证样本：只就这一个身份，就能确认 120 次“不再工作但仍请求模型”的成功调用。由于二代没有持久化 usage，这 120 次不能精确折算 token 或人民币，也不能外推成全体比例。

#### 放大器 5：重复启动与无成本遥测

同 id 多 PID、launcher retry、O_TRUNC、无锁 session manifest 让实际并发与身份计数脱节。direct runner 完全忽略 provider usage 字段，没有 per-agent token、currency、budget 或 cost kill switch。系统只能在钱花完后看日志猜规模。

### 6.4 为什么“缩短会话”比“减少输出”更重要

Completion 只占 0.398%。限制 agent 写少一点文本不会解决主问题；需要限制的是：

- 历史上下文长度；
- 总 outer turns；
- tool round 数；
- 重复/未处理消息注入；
- 并发与重复 lifecycle；
- 高档模型覆盖率。

## 七、下一轮的实验与预算方案

### 7.1 默认只允许小 pilot

建议把默认从“大规模开放运行”改成：

| 阶段 | 默认上限 | 晋级条件 |
|---|---|---|
| smoke | 3 agents × 5 turns，低档模型 | runner、ledger、usage、停止、身份签名全部通过 |
| pilot | 6 agents × 20 turns，最多 2 小时 | 预注册指标可计算；无 duplicate process；预算曲线可预测 |
| confirmatory | 最多 12 agents × 50 turns | 明确批准 token/RMB hard cap；冻结代码与 baseline |
| large | 36+ agents 或 50+ turns | 必须单独审批，不作为默认探索模式 |

现有 `maso_guard.sh` 只是 best-effort 本地进程护栏：它检查 `running > 8`；变量名叫 `MAX_TURNS` 的条件实际读的是单 session `message_count > 60`；所谓 `MAX_DAILY_MSGS` 实际是当前 API 返回集合中 `message_count` 求和 >8000，没有日期过滤。API 空或解析失败时它 fail-open `exit 0`；越界后仅 `pkill` 本地 `MASO Cowork`/`Downloads/swarm` 相关进程，不验证 cutoff 后零新请求，也不覆盖 devbox direct runner。因此它不能当可核验预算器；两条执行通路必须共享同一个独立、fail-closed 预算控制面。

### 7.2 预算必须 fail closed

每个 run 预先写死并由独立 supervisor 执行：

- `max_currency_rmb`；
- `max_total_tokens`；
- `max_prompt_tokens_per_request`；
- `max_requests`；
- `max_outer_turns`；
- `max_tool_rounds`；
- `max_wall_clock`；
- `max_concurrent_processes`；
- `max_processes_per_agent_id = 1`。

任一命中立即停止新请求、持久化 state、生成结算；supervisor 必须与 agent 不同 uid，agent 不可写 budget、PID 或 usage ledger。

### 7.3 尊重完成与去重社会刺激

Runner 必须有显式状态机：

```text
RUNNING → QUIESCENT → STOPPED
```

- agent 输出结构化 `done=true` 或连续两轮 `no_action` 后进入 QUIESCENT；
- 没有新 board event 时不再调用模型；
- 每个 agent 保存 `last_seen_message_event_id` 与 `last_seen_stimulus_hash`；
- 同一消息/刺激只进上下文一次；
- 新事件到来才唤醒，而不是固定轮询 200 次。

### 7.4 保存完整且可计费的原始记录

每个 API request 至少落：

- signed `process_instance_id`、agent role、host、pid；
- request/response id、model、reasoning tier；
- prompt/completion/cache usage；
- currency estimate 与价格表版本；
- input event ids、tool calls、artifact hashes；
- stop reason；
- 完整对话或可恢复的内容寻址历史。

没有 usage 和 history 的 runner 不得进入大规模阶段。

### 7.5 修复 actor 与 ledger

- 每次启动生成不可伪造的 `process_instance_id`；所有 artifact/message/citation 由实例签名。
- `agent_id` 只表示实验角色，不作为作者主键。
- predecessor 必须 terminate + verify 后才允许 successor；若双实例是 treatment，必须显式随机化。
- event ledger 保持不可变，但 canonical view 必须支持 `active/superseded/retracted/disputed`。
- citation 拆成 `provenance / used / replicated / corrected / inspired / alliance`，不再用 raw edge 计存续。

### 7.6 如果要研究社会机制，必须冻结与随机化

- 同一 epoch 冻结 launcher、runner、reaper、parser、paths、model map 和 baseline hashes。
- 任一 hot patch 自动结束 epoch，不能前后合并。
- 每个 island 从同一 content-addressed baseline 开始，或把 baseline 随机化并记录。
- treatment assignment、model、host、launch time 正交化。尤其不能重复本轮 wave 2 的确定性配置：101–1000 中唯一 treatment 是 agent-0150，它必然落在 122456，因而该个案与 host/model/launch-time 完全共线；wave 1 另有 5 个 assignment，其中落在 122447 的两个全部 import 失败。
- adversary 身份和 source 不应对被试可读；如果研究透明度，就把 disclosure 随机化成 treatment。
- 预注册 actor unit、outcome、citation profile、exclusion 和停止规则。

## 八、最后的研究判断

### 这次花的钱有没有留下价值？

有，但价值不在最初想证明的那些宏大 headline 上。

没有被支持的是：真实 selection 导致 specialization、1000-agent 全局社会、稳定 disciplines、干净 adversarial resilience。

真正留下来的，是一套相当丰富的机制语料：

1. 公开制度如何在没有执行时仍塑造行为；
2. 共同可见性如何制造基础设施拥挤；
3. 拥挤如何把部分 agent 推向验证 niche；
4. 可执行反例如何跨 agent 产生修复；
5. 纠错规范如何进一步产生过度纠错；
6. append-only 如何同时保存问责和错误；
7. 身份、文件和 process 的错位如何破坏社会测量；
8. 信息孤岛如何让局部理性产生全局错误；
9. 技术协议如何成为社会制度；
10. 缺乏退出语义如何同时烧钱并污染行为。

最值得带到下一轮的不是“再开更多 agent 看会不会更涌现”，而是三个可检验问题：

- **可见性排序是否比 artifact 质量更能预测早期扩散？**
- **单边可验证/可采用的修复是否比需要多人协调的协议更容易传播？**
- **纠错奖励超过什么强度后，会从提高真实性转为诱发 false retraction？**

这三个问题都可以先用 6–12 个 agent、严格身份、冻结制度、完整 usage 和几十轮以内的受控 pilot 做初步检验，不需要再付一次 30 万才知道机制是否值得追。如果要得到 confirmatory 结论，还必须根据效应量、cluster/island 数和 outcome variance 事先做 power analysis，不能默认 6–12 就足够。
